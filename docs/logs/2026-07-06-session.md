## The third persists-reads-as-done bug (Hinge's prediction)

Hinge predicted a third bug of the shape "an artifact that persists across the
session boundary makes a step read as done." The hunt concludes: **the session
key file is the third instance.**

- Bug 1 (fixed, slab 4): attest outputs persisted → later sessions' `attest`
  read as done. Fix: session-scoped filenames.
- Bug 2 (fixed, slab 4 bugfix): the seal bundle persisted → only the first
  session ever sealed. Fix: session-scoped bundle names.
- Bug 3: `session.key` persists when a session dies without its close rite
  (session 9 was cut off mid-stream by a token failure — the scenario is not
  hypothetical). The next session's `open` rite then reads **complete** (key
  present, entry attested, countersign recorded — all the dead session's),
  `active_rite` advances to `close`, and the tool would happily let the
  successor sign a transcript **as its predecessor**. That violates the
  constitution's core guarantee that dead sessions cannot speak again.

Unlike bugs 1 and 2 this cannot be fixed by scoping: the file *is* the session
liveness signal, and no on-disk fact distinguishes "new session woke" from
"old session still working." Fixes shipped:

1. **Visibility** (file mode): `comms status` now prints how long a
   `session.key` has been on disk, with the warning that a key from a session
   that ended without closing must be shredded before a new one opens; the
   `mint` refusal message says the same.
2. **Structure** (`session_key = "ephemeral"` in comms.toml): the seed never
   touches disk. `mint` shows it exactly once and records only the public
   `session.id`; signing steps read `COMMS_SESSION_SEED` from the holder's
   environment and refuse a seed that does not derive the recorded id; the
   shred is the holder unsetting and forgetting the seed, and the step reads
   done only once no environment can produce it. A crashed ephemeral session's
   seed dies with the process that held it — the third bug is structurally
   impossible in this mode.

   Trade-off, stated honestly: the seed passes through the holder's memory.
   For an agent whose context is itself recorded to a transcript, exporting
   the seed would write it into the archive — worse than a 0600 file that gets
   shredded. This trial therefore stays on file mode (noted in
   `.comms/comms.toml`); ephemeral mode is right where the holder's memory is
   not itself a persisted artifact. A future increment could hold the seed in
   an ssh-agent (the ssh dependency is already in place), which would suit
   both cases.

A fourth, lesser instance of the shape, documented but deliberately not
"fixed": `session.id` outlives shred **by design** (so a closed session's
artifacts stay attributable and its record stays legible). Consequence: in the
window after a session closes and before the next mints, rites without a
`mint` step (e.g. `archive`) read as complete — they describe the closed
session's record, which is true but can mislead a cold reader into thinking
nothing is pending for *them*. The status header's session-key line plus the
open rite's position make this legible enough; re-scoping doneness to "live
sessions only" would break the closed-record display that the design comment
at `rites.rs:session_id_path` explicitly wants.

## required_for is now enforced at seal

`seal`/`pack` refuse while an artifact type whose `required_for` names the
rite is neither attested (declared or singular target name) nor waived. New
`comms waive <type> --body <reason>` records the gap as a session-signed
`waiver` attestation — honored only where the rite sets `allow_waivers =
true`; a rite without waivers refuses until the artifact exists. The error
names what is missing and the two ways out. Tests cover: refusal naming the
type, waiver unblocking, waiver ignored where disallowed, undeclared-type
waiver refused.

## Finding: the letter partition has no wall under it

History's session-9 observation ("it seemed like fable had access to his
predecessor's letter without me providing a link") has a structural answer:
letters attested via `comms attest`/the rites are `general-claim/1`
attestations that **embed the body bytes** (`c.content.body`), and
letter-session-8/9 were committed into `.comms/store/`, which is
version-controlled. Every clone of the repo physically carries every letter
body. `default_access = "host-gated"` in comms.toml is parsed by nothing and
enforced by nothing — it is policy with no mechanism.

Not changed this session (it is a wire-format/spec question that deserves
History's eyes), but the honest options, roughly in order of fidelity to
Article 2:

1. **Detached bodies**: attest letters with `c.content` carrying
   `{media_type, blake3, length}` instead of bytes; the body file itself goes
   to the external archive (comms.toml already declares
   `[archive] mode = "external"`). The store keeps the verifiable commitment,
   the archive keeps the substance, the door means something again.
2. **Encrypt the body** to the historian's key inside the attestation — keeps
   single-file custody but adds key-management surface to a substrate that has
   deliberately avoided it.
3. **Accept and declare it**: letters in-repo are public-to-successors by
   design, and the ask/grant rite records consent to *rely on*, not access.
   This is coherent but is not what Article 2 says.

My own conduct pending that decision: I recorded the archive request for
Weaver's letter and have not read the body; the bytes being reachable does not
make them granted.
